# Run as one per-user tray process, not a Windows service

UsageQuotaTray runs as a single unelevated process in the user's session, started at sign-in from the current user's `Run` key. We rejected a least-privilege Windows service plus a UI process. Services run in session 0 and cannot show the tray icon, popup or toasts ("Services cannot directly interact with a user as of Windows Vista", [Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)), so a per-user UI process would be needed anyway. The low-privilege service accounts (LocalService, NetworkService, virtual service accounts) cannot read the Assistants' credential files in the user's profile. Every way around that grants more privilege or breaks our rule that third-party credentials are read-only: running as LocalSystem, storing the user's password in the service configuration, or changing the third-party file's permissions. App secrets would also have to move from user-scope DPAPI (Data Protection API) to machine-scope DPAPI, which any local process can decrypt. Finally, installing a service needs admin rights, which an unzip-and-run release avoids.
